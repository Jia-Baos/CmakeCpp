## 代码解析

- Elevator 类（上下文）：它代表了电梯的上下文，持有当前的状态对象，并委托状态相关的行为（如按键、开门、关门、开始移动等）给当前的状态对象。它还能够在状态变化时切换状态。

- ElevatorState 类（状态接口）：它是一个抽象类，定义了电梯的行为接口，这些行为包括按下按钮、开门、关门和开始移动。每个具体状态都实现这个接口，来定义不同状态下的具体行为。

- StopState 类（具体状态）：它代表电梯处于停止状态时的行为，例如，按下按钮时会让电梯开始移动，开门时会让电梯进入开门状态。

- MovingState 类（具体状态）：它代表电梯处于移动状态时的行为。例如，当电梯在移动时，按按钮、开门等操作都会受到限制。

- OpenDoorState 类（具体状态）：它代表电梯门打开时的行为，例如，电梯门开着时，无法移动，但可以关闭电梯门。

- 主函数：在 main() 中，创建一个 Elevator 实例并模拟电梯的操作。通过调用 pressButton()、openDoor()、closeDoor() 和 startMove() 方法，电梯状态会根据当前的状态变化而发生相应变化。

## 优点

- 避免多重条件判断：状态模式避免了使用多重条件判断来决定对象的行为。每个状态类都只负责自己状态下的行为，逻辑更加简洁和清晰。

- 状态转换清晰：不同状态下的行为被分隔到不同的类中，使得状态切换的代码更加清晰和易于管理。

- 扩展性强：如果需要新增状态，只需创建新的状态类并实现状态接口，而无需修改现有的代码。

## 缺点

- 类的数量增加：状态模式会引入许多状态类，如果状态种类很多，可能会导致类的数量急剧增加。

- 复杂性增加：对于一些简单的状态转换，状态模式的引入可能显得过于复杂。

## 适用场景

- 有限状态机：如交通信号灯、手机待机状态等。

- 对象的行为在不同状态下变化时：例如电梯、游戏中的角色状态、网络连接的状态等。

- 避免大规模的条件判断：如果你发现代码中有大量的 if 或 switch 来判断对象的状态，可以考虑使用状态模式来重构代码。
